# HondataDash V2.0.1-internal.3 / V2.0.T3

## IT3 HF2（2026-09-20 Session 消失排他性热修）

HF1 实车再次确认：行驶过程中 `Diagnostics/YYYYMMDD_HHMMSS_IT3/` 目录及数据文件真实存在并持续增长，但停车熄火、车机断电、再次上电准备复制时 Session 目录消失。该证据排除了“未 commit / 未授权 / 首次写盘失败”为主因，并把问题收敛到启动恢复阶段或车机存储层。

HF2 采取排他性诊断策略，不改变任何产品语义：

- build identity: `2.0.1-internal.3-hf2` / versionCode `49`
- launcher: `Hondata Dash IT3 HF2`
- **完全暂停 Recorder 自动 retention**：HF2 源码中移除 `enforceRetention()`、`deleteRecursively()`、1 GB/30 Session 自动清理阈值；App 本身不再具备递归删除 Session 目录的代码路径。
- 启动只执行 interrupted-session marker recovery，不执行任何 Session 目录清理。
- `ACTIVE -> POWER_CUT_RECOVERED` 改为先成功创建 `POWER_CUT_RECOVERED`，再删除 `ACTIVE`；若新 marker 创建失败则保留 `ACTIVE`，下次启动重试。
- HF1 的 Bluetooth lifecycle 修复、1 s stable drive gate、fsync warning 降级全部保留。
- SHIFT/DFCO/Recovery/Fuel Pressure/MAP Last Boost Event/UI/50 Hz polling 全部保持冻结。

HF2 是故障归因构建：如果熄火再上电后 Session 不再消失，则 startup retention 路径被实车坐实；如果仍然消失，则 App 已无目录删除能力，问题必须转向车机系统的 shared-storage 挂载/清理机制。

## IT3 HF1（2026-09-20 实车生命周期热修）

道路验证发现两个基础设施问题，因此在不进入 IT4、且不改变 SHIFT/DFCO/Recovery/UI 产品语义的前提下发布 HF1：

- build identity: `2.0.1-internal.3-hf1` / versionCode `48`
- launcher: `Hondata Dash IT3 HF1`
- Recorder drive commit 改为复用产品已有的 `RPM >= 500` 持续 `1 s` stable gate，单帧高于 500 rpm 不再直接 qualify；
- Bluetooth lifecycle pause 增加 poll-worker ownership handoff：快速从空调/电话/油耗页面返回时，不提前清除 pause 状态；pause 窗口中的 read termination 不再先把 `connected=false`，恢复后优先沿用原 RFCOMM socket，只有恢复后的真实 I/O failure 才进入 full reconnect；
- atomic metadata/stats 仍保留 `tmp -> flush -> rename`，但老车机若仅 `FileDescriptor.sync()` 无法提供物理同步保证并抛 `SyncFailedException`，降级记录为 `syncWarnings`，不再永久关闭 Recorder；普通 IOException 仍按真实写盘失败处理；
- 继续保留 copy-only ignition 不创建驾驶 Session、ACTIVE/POWER_CUT_RECOVERED、10 s stats checkpoint、约 2 s trace/raw flush 等 IT3 设计。

HF1 的首要实车验收是：正常切换空调页面后优先直接恢复 LIVE；返程长驾驶必须形成完整 IT3 Session，重新通电后应为 COMPLETE 或 POWER_CUT_RECOVERED。

## 定位

IT3 是基于 IT2 实车 Flight Recorder 证据形成的第一轮 evidence-driven refinement。

版本身份：

- versionName: `2.0.1-internal.3`
- versionCode: `47`
- applicationId: `io.github.asteroidb612zs.hondatadash.internal`
- launcher: `Hondata Dash IT3`
- branch: `internal/v2.0.1-it3`
- source base: IT2 `04e952d18b00bee8a7a83019b7e1b49e2e9024e5`

本版本处理四类已获得实车证据的问题：

1. BT42 无 Clutch.Pos 时 SHIFT legacy fallback 过度确认；
2. reconnect placeholder frame 可错误初始化 ThermalContext/MainState；
3. MAP MAX 8 s rolling recent peak 不符合“刚才这一脚增压峰值”使用需求；
4. IT2 Recorder session 生命周期与车机真实“点火自动启动 / 中途切后台 / 熄火直接断电 / 再通电拷文件”流程不匹配。

## 1. BT42 SHIFT

IT2 实车 manifest 确认当前车机 FlashPro Bluetooth session：

- ChannelCount = 42
- Gear 可用
- Clutch.Pos 不可用

因此 IT3 将运行路径分为：

### 完整 Clutch 路径

若 Clutch.Pos 可用：

保持 IT2/IT1 原有 ShiftPhase 逻辑。

### BT42 路径

若 Gear 可用但 Clutch.Pos 不可用：

- RPM/Throttle legacy trajectory 只能进入 `SHIFT_ARMED`；
- trajectory 不允许直接进入 `SHIFT_CONFIRMED`；
- `Gear` 新档位连续稳定 100 ms 后，才成为 authoritative SHIFT confirmation；
- BT42 armed-only fuel cut 不再强行分类为 SHIFT_FUEL_CUT；
- 真正 confirmed Gear shift 仍可分类 SHIFT_FUEL_CUT；
- armed timeout = 650 ms；
- stable Gear confirmation bridge 继续使用 420 ms。

两份长 Hondata LOG 的离线验证：

- 20260527：100 ms-stable Gear transition 95 次，95/95 均存在真实 Clutch.Pos 动作证据；
- 20260603：97 次，97/97 均存在真实 Clutch.Pos 动作证据。

因此 Gear-stable transition 被用于 BT42 authoritative confirmation。

## 2. reconnect placeholder gate

IT2 实车记录发现：

Bluetooth reconnect 后第一帧可出现占位/哨兵值，例如：

- RPM = 0
- ECT = -17.78 C
- throttle = negative placeholder

该帧曾导致热机错误进入 COLD/WARMING/WARMUP。

IT3 在 `EngineStateTracker.update()` 之前加入 critical transport plausibility gate。

只使用物理不可能范围判断，不使用 ECT 最低温度限制，因此真实寒冷启动不会仅因低 ECT 被拒绝。

关键范围：

- RPM 0..10000
- Speed 0..350
- MAP 10..400 kPa
- Throttle Plate 0..100%
- Injector 0..50

被拒绝帧仍可保留 raw Bluetooth evidence，但不得初始化 semantic state。

## 3. MAP MAX = Last Boost Event Peak

IT2：

- MAP MAX 为 rolling recent maximum
- hold 8 s
- 之后 tau=3 s 向当前 MAP 衰减

IT3 改为：

**Last Boost Event Peak**

### Boost event start

同时满足：

- ThermalContext 非 COLD/WARMING
- 非 Shift / 非 fuel-cut
- RPM > 1500
- Throttle Plate > 35%
- raw relative boost > +0.20 bar

### Peak capture

- 使用 raw relative MAP，而不是经过 Boost display filter 的值；
- event 内只允许合法非 fuel-cut / 非 shift sample 更新 peak；
- peak 不使用 rolling cooldown/decay。

### Event bridge/end

为将多挡连续一脚油门视作一个 boost event：

- shift active 本身保持 event；
- throttle > 20% 或 boost > +0.10 bar 保持 event；
- 连续 1800 ms 无 demand 后结束 event。

### 显示语义

- event 进行中：MAX 实时显示本次事件目前最高值；
- event 结束：锁存最后一次 boost event peak；
- 不按时间衰减；
- 直到下一次 boost event 开始才重置为新事件 peak；
- 本次发动机运行周期尚未出现 boost event 时，MAP MAX 显示 `--`；
- MAP MIN 继续保留原 recent vacuum 逻辑。

## 4. Recorder 真实车机生命周期

真实使用流程：

1. 点火；
2. 车机约 1 s 后自动启动 HondataDash；
3. 行驶中可能因电话、油耗、空调等切出仪表；
4. 到目的地熄火，车机直接断电；
5. 如需复制 LOG，再次通电；
6. HondataDash 自动启动；
7. 不启动发动机，仅进入文件管理器复制旧 LOG；
8. 再断电离车。

IT3 Recorder 改为：

**一次发动机运行 = 一个驾驶 session**

### Engine-run gate

- App 启动或 Bluetooth connect 不等于建立 session；
- 只有 plausible telemetry 中 RPM >= 500 时才 `driveQualified`；
- 点火但发动机未启动、仅为了复制文件时：
  - 不创建新 session；
  - 不写新的驾驶文件夹；
  - 仅在 RAM 中保留最多 64 个 raw pre-roll frame。

### Pre-roll

首次 engine-running sample 到来时：

- 提交 drive session；
- 把此前最多 64 个 raw frame 作为启动前短 pre-roll 一并写入。

### UI background

Activity onPause 仍保持现有生产策略：

- `dataSource.stopPolling()`

IT3 不改变 Bluetooth background policy。

但 Recorder 不再因为 60 s 无 frame 自动关闭 session。

因此：

- 接打电话；
- 查看油耗；
- 调空调；
- 返回仪表

仍属于同一个驾驶 session，只在数据中形成 gap。

### Engine stop

若车机仍供电且 RPM <=300 持续 5 s：

- 正常关闭当前 Recorder session；
- 写 COMPLETE。

### 直接断电

每个已提交 session 创建 `ACTIVE` marker。

若车机直接掉电来不及收尾：

下次 App 启动、Recorder 存储可用后（**不等待 FlashPro 协议握手完成**）：

- 发现旧 `ACTIVE`
- 删除 ACTIVE
- 写 `POWER_CUT_RECOVERED`

该状态表示：

“车辆正常直接掉电导致的非优雅关闭”，不是应用崩溃。

### Copy-only power-up

下次仅通电拷文件时：

- 旧 ACTIVE 自动转换为 POWER_CUT_RECOVERED；
- RPM 未达到 500；
- 不新建 IT3 session。

因此文件管理器看到的就是上一趟真实驾驶文件夹，不会多一个复制阶段的小 LOG。

## 5. Recorder crash safety

IT3：

- `session.json.tmp -> fsync -> rename session.json`
- `recorder_stats.json.tmp -> fsync -> rename recorder_stats.json`
- stats 每 10 s checkpoint
- 每 session 独立重置 counters
- raw/csv 继续每约 2 s flush

这样直接断电时：

- 主 trace 最多只损失尾部小窗口；
- metadata 不应再出现 0-byte 正式文件；
- stats 即使来不及最终 close，也保留最近 checkpoint。

## 6. Extrema recorder reset

IT2 reconnect/reset 后 Recorder 自己的 extrema cache 未同步，可能把 MAX reset 误记成：

`82.77 -> 81.66 ADMITTED_UPDATE`

IT3：

- product extrema reset 时调用 Recorder `onExtremaReset`
- Recorder 清该 card 的 cache
- 写 `EXTREMA_RESET` event
- 下一次值重新按 INITIALIZE 记录

## 7. Event log noise

IT2 长 session 中大量 40-100 ms TIP_IN/TIP_OUT/BOOST_SURGE modifier transition 使 events.csv 膨胀。

IT3：

- `semantic_trace.csv` 继续逐行保存 Modifier；
- `events.csv` 不再镜像每个 generic MODIFIER transition；
- 保留 ShiftPhase、Combustion、Admission、Fuel Pressure、Boost Event、UI foreground/background 等高价值事件。

### 实车

3. 热机 Bluetooth reconnect：不再出现 COLD/WARMING/WARMUP 假状态；

   - MAP MAX 锁存该次 event peak；

   - 下一次 boost event 自动切换为新事件 peak；
5. 电话/空调/油耗页面切出再返回：
   - 仍在同一个 session 文件夹；
6. 到目的地直接断电；
7. 再次只通电、不启动发动机、打开文件管理器：
   - 上一 session 为 POWER_CUT_RECOVERED 或 COMPLETE；
   - 不出现新的 copy-only session。
