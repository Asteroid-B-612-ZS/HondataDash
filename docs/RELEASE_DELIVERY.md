# 正式版本交付规则

适用于 HondataDash 正式 APK 的发布、补传和验收。保留现有产品测试、实车验收、离线签名和正式发布授权要求；合并流程修复本身不构成新版本发布授权。

## 完成条件

只有 `scripts/release_delivery.py audit` 输出 `VERIFIED_PUBLIC_DELIVERY`，才可以报告“正式发布完成”。验证器必须确认：

1. 已批准的 `release/manifests/vX.Y.Z.json` 存在，校验文件未被改写。
2. 远程 Tag 指向清单中的完整源提交 SHA，源码包名、版本号、版本代码和 API17 身份匹配。
3. 该准确源提交的最新 Production CI 运行成功；其他提交、其他工作流、PR 合成提交或旧的成功记录不能替代。
4. 正式 APK 和校验文件都在 Release 中，大小和 SHA-256 正确。
5. 实际下载的 APK 通过 Android 包身份检查和 `apksigner verify`，签名证书与批准值匹配，具有 API17 所需的 v1 签名，且不是 debuggable APK。
6. 正式发布后，未携带身份令牌的公开下载成功，下载内容仍与批准值一致。

Release 页面存在、Actions 绿色、校验文件存在、APK 只保存在本地，均不能替代上述交付检查。校验失败应报告明确缺项，不能重新计算批准哈希来“修复”不匹配。

## 离线签名与新版本

私钥继续离线保存，不进入仓库或 Actions。验证器处理已签名 APK，不生成密钥、不重新签名，也不创建或移动 Tag。

每次新版本按既有实车/产品验收要求取得发布授权后：

1. 固定拟发布源提交，等待该提交的 Production CI 通过；新 Tag 必须指向该提交。
2. 在批准的签名环境生成 APK，保留原始安装包和私钥的独立备份。
3. 在独立 PR 中新增清单、校验文件和发布说明。清单记录源 SHA、应用身份、APK 文件名/字节数/哈希、签名证书指纹和是否设为 Latest。批准值应来自已验收产物，不在发布任务中临时生成。
4. 审核并合并清单。公开 Release 尚未创建时，自动审计继续检查当前 Latest，因此不需要先发布空壳版本来使 CI 通过。
5. 用下列本地交付命令，或“草稿 + 手动工作流”完成本次已授权发布。

新增清单不代表修改已发布版本的批准值。发布说明、Tag、APK 与源提交之间的对应关系必须可追溯。

## 本地交付与缺附件补传

环境：Python 3.11+、GitHub CLI、JDK 和 Android Build Tools；`gh` 已对本仓库完成正常授权。将 `aapt` 和 `apksigner` 放入 PATH，或通过同名参数指定工具路径；`--apksigner` 也支持官方 `apksigner.jar`。

先验证已签名文件（此命令不访问 GitHub，也不表示公开交付完成）：

```bash
python3 scripts/release_delivery.py verify-local --tag v3.0.0 --apk /path/to/HondataDash_V3.0.0.apk
```

执行已经获准的交付或补传：

```bash
python3 scripts/release_delivery.py deliver --tag v3.0.0 --apk /path/to/HondataDash_V3.0.0.apk
```

行为：

| 远程状态 | 处理 |
|---|---|
| Release 不存在，已提供合格 APK | 创建草稿，上传必需附件，下载校验，通过后公开，再验证公开下载 |
| Release 不存在，未提供 APK | 失败，不创建空 Release |
| 已有草稿，已放入合格 APK | 校验已有附件、补齐校验文件，通过后公开并验证下载 |
| 已公开，缺 APK | 只补传已提供且验证通过的原始 APK；保留发布属性和既有附件 |
| 已公开，缺校验文件 | 从已批准清单对应文件补齐，再验证下载 |
| 同名附件完整且一致 | 验证后跳过，不重复上传 |
| 同名附件内容不同、未上传完毕或身份不符 | 报错，不覆盖、不删除 |
| 上传中断 | 返回失败；新版本保留草稿。再次执行时验证已有文件，仅补缺项 |
| 已公开但下载失败 | 返回失败，不宣称交付成功；检查服务状态后重跑审计 |

禁止使用 `--clobber` 自动替换正式附件。冲突需查明来源并按单独授权处理。

## 草稿 + 手动工作流

使用 GitHub 页面时，先创建**草稿**并附加离线签名 APK。随后在默认分支运行 `Release Delivery`：

- `mode=audit`：只读检查。标签留空时检查当前 Latest；给定标签时检查对应清单。
- `mode=deliver`：明确执行本次已经批准的正式发布，必须填写 `vX.Y.Z` 标签。只能从已审查的默认分支执行。工作流验证草稿中的 APK，补齐校验文件，通过后公开。

GitHub 手动工作流不接收本地文件；缺 APK 必须失败。可先通过页面将原始 APK 附加到草稿，或使用上面的本地 `--apk` 命令。已经公开的版本需要补传时，同样可以使用本地命令；页面补传后必须再运行只读审计。

`deliver` 不得由普通 push、PR 或 release 事件自动触发。默认分支合并、PR、发布/编辑 Release 事件只运行只读验收。工作流中的发布权限仅赋给手动发布 job，Actions 权限仅为 read。

## 检查与证据

```bash
python3 -m unittest discover -s tests -p 'test_release_delivery.py' -v
python3 scripts/release_delivery.py audit --tag v3.0.0
```

不指定 `--tag` 的审计检查当前 Latest。不存在清单的历史版本无法被该验证器宣称已验收；需要先补充可追溯清单。

失败场景测试使用本地 GitHub 状态模拟，不发布测试版本、不上传虚假 APK。CI 的 `audit` job 则下载真实公开 APK，检查真实包身份和签名。原有 Production CI 也在指向 master 的 PR 上执行，不能以流程单元测试替代产品检查。

验收成功后，终端 JSON 与 Actions Summary 包含源提交、源 Production CI 链接、Release 链接、APK 下载链接和批准哈希。AI 应提供这些可核对的证据；工具无上传能力或操作受阻时，必须报告未完成，不能改为只发布文本或校验文件。

## 清理与回退

发布流程不删除远程分支、Actions 产物或 Release 附件。历史清理由独立、明确范围的任务处理，并遵守既有授权和保存要求。不得在缺附件或验收失败时执行清理。

本次修复退役旧的 `v300-publish.yml`：它在每次 master push 上发布/跳过后继续宽泛清理。需要暂停新发布时，停用手动发布入口即可；不要恢复旧的自动清理流程。流程修复不改动产品源码、版本号、历史 Tag 或正式签名身份。
